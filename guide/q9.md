# Q9 guide: How will you work the long tail, stop, and learn from failures?

For question 9 of the [checklist](../checklist.md): read it before writing up a finding on that
question. It walks through what the cases show; the project's owner decides. Each point names its
evidence: a lesson ID (its strength, its cases and the cases against it are in
[lessons/evidence.md](../lessons/evidence.md); its page links the case sections) or a case link.
"(ours)" marks the maintainer's reading, evidence level `ours`; so does a lesson tagged `[ours]` there,
which is our inference from its cases.

## Lessons behind it

- [VER-3](../lessons/verification.md): a failed unit retried with its latest errors in a fresh
  prompt, a bounded number of times, then handed to people; it fits independent units.
- [KNW-1](../lessons/knowledge.md): when a failure recurs, what generates the code is fixed, not
  only the output; the second time is the trigger.
- [KNW-2](../lessons/knowledge.md): each unit stamped with its status, the largest failing group
  tuned on a sample, then everything swept again.
- [KNW-4](../lessons/knowledge.md), [KNW-5](../lessons/knowledge.md): the method kept in files a
  fresh session rereads; temporary migration code marked when written.
- [OVS-3](../lessons/oversight.md): where automation hands over to people decided up front.
- [OVS-5](../lessons/oversight.md): small waves with a person's approval between them.
- [CTX-7](../lessons/context.md): the agent asked after each session what its prompt lacked.
- [AGF-7](../lessons/agent-failures.md): output varies between runs on the same input.
- [OPS-6](../lessons/operations.md): bulk jobs in scheduled batches, results sorted by status,
  only the stuck ones rerun.
- [ROL-8](../lessons/rollout.md): a unit that fails its tests sent back to the old framework.
- [TST-11](../lessons/testing.md): a golden set rerun after each prompt change.

Cases, in our words: Airbnb stamped each file with its status, swept again after each fix and
finished the last files by hand; Intel capped retries. GitHub turned repeated failures into
instructions, skills and evals; Spotify asks the agent what its prompt lacked; Zalando reran a
golden set after each prompt change. Uber put files whose tests failed back on the old framework.
ts-rust's first attempt stalled for months, no stop rule stated; Spartacus now stops for a person
after each wave.

## What it looks like in a project

- A plan that retries every failing unit until it passes, with no bound and no hand-over
  ([Airbnb](../cases/2025-04-01-airbnb-enzyme-to-rtl.md#what-worked), [ts-rust](../cases/2026-10-07-ping-tsgo-to-rust.md#what-went-wrong)).
- Units that depend on each other, where a failure downstream often comes from a wrong unit
  upstream (VER-3's "Against").
- The same failure fixed by hand in many outputs, with no change to the prompt or tool that made it
  (KNW-1).
- No status per unit, so a rerun redoes what already passed (KNW-2).

## Questions to ask of this project

- Which units are independent, and which depend on others?
- Where is each unit's status kept, and can a failing unit be rerun from the step that failed?
- After how many attempts, or what signal, does a unit go to a person?
- Where does a failure seen twice become an instruction, a skill or an eval?
- What is the rule for stopping the automation as a whole?

## Trade-offs

- A bound on retries saves attempts on units that will not pass and sends some units to people
  that one more try would have fixed (VER-3; rows P6 and P9 of the checklist's Provenance table).
- Fixing the prompt or tool after a repeated failure costs a rerun of everything it made, and
  saves fixing each output by hand (KNW-1).
- Waves with a person's approval between them contain a systematic mistake and slow the run
  (OVS-5).

## When not to apply it

- A count of attempts suits small independent units such as files; for units in a chain, fixing
  the workflow and rerunning from the first wrong unit fits better (VER-3, row P6).
- Airbnb's numbers come from test files of simple and medium difficulty; they say nothing about
  packages or services (VER-3; row P9 of the checklist's Provenance table).
