# Q2 guide: Is there a test oracle that survives the move and that the agent cannot edit?

For question 2 of the [checklist](../checklist.md): read it before writing up a finding on that
question. It walks through what the cases show; the project's owner decides. Each point names its
evidence: a lesson ID (its strength, its cases and the cases against it are in
[lessons/evidence.md](../lessons/evidence.md); its page links the case sections) or a case link.
"(ours)" marks the maintainer's reading, evidence level `ours`; so does a lesson tagged `[ours]` there,
which is our inference from its cases.

## Lessons behind it

- [TST-1](../lessons/testing.md): a black-box suite that does not depend on the language judged
  the port, run against old and new.
- [TST-2](../lessons/testing.md): the missing-feature regressions came from behaviour no test
  covered.
- [TST-3](../lessons/testing.md): matching the old system does not make the port right; a
  faithful port carries the old bugs.
- [TST-4](../lessons/testing.md): checks compiled only into debug builds hid release-build
  regressions.
- [TST-5](../lessons/testing.md): where tests were thin, recorded inputs and outputs of the old
  system stood in.
- [TST-6](../lessons/testing.md): a red baseline or golden files that cannot be regenerated stall
  correct changes.
- [TST-8](../lessons/testing.md): when tests are what moves, passing proves little; counts,
  coverage and intent need comparing.
- [TST-10](../lessons/testing.md): one generation writing both code and tests invites tests that
  cannot fail.
- [TST-12](../lessons/testing.md), [TST-13](../lessons/testing.md): old and new compared on what
  users and other systems see, side by side on the same inputs.
- [TST-14](../lessons/testing.md): coverage rose while agent-written tests asserted nothing.
- [TST-15](../lessons/testing.md): a harness simpler than production let a production bug through.
- [VER-5](../lessons/verification.md): a green run can hide tests that never ran.
- [VER-11](../lessons/verification.md): how late a wrong change first fails shapes the pipeline.
- [OVS-1](../lessons/oversight.md): the agent that changes code should not change what counts as
  correct.

Cases, in our words: GitHub's unchanged end-to-end suites were the oracle; its feature-loss
regressions came almost all from their gaps. Bun's suite, in a third language, judged the whole
port (a critic notes it missed the old bugs). Google's correct changes stalled on failing tests
and goldens; Spotify's worst case is green CI with wrong behaviour. Intel, Shopify, ts-rust,
Pokémon and Ladybird ran old and new on the same inputs (Ladybird also edited its expected outputs
in that change). Bloomberg's changes could fail only once deployed; Checkly's harness passed while
production retries failed.

## What it looks like in a project

- Tests that drive the product from outside (a CLI, an API, files written) survive a language
  change; unit tests tied to the old code's internals usually do not, unless they are ported too ([GitHub](../cases/2026-09-16-github-copilot-runtime-rust.md#how-it-was-checked), [Bun](../cases/2026-07-08-bun-zig-to-rust.md#how-it-was-checked)).
- Golden files and snapshots that only the old implementation can regenerate (TST-6).
- A suite that is green while some tests are skipped or never collected (VER-5).
- No rule on who may edit a test: the agent can make a failing check pass by changing it (OVS-1,
  AGF-5).
- Results the old system already made and kept (saved results, rendered files, rows) that must
  stay exactly as they are, with no test fixture holding one: green tests then say nothing about
  them. One proof is a copy of the live store on which old and new code each process all of it,
  outputs compared (ours; seen in a change of engine in the maintainer's own project, not a
  published case; near TST-5 and TST-13).

## Questions to ask of this project

- Which public features have no test that drives them from outside?
- Which tests fail or will not run today, before any change?
- Can old and new run the same inputs, with outputs compared, and what varies per run?
- How late does a wrong change first fail here: at build, in tests, or only once deployed?
- Who must approve a change to a test, a snapshot or a baseline, and what enforces it?
- Which kept results must stay unchanged, and how will a copy of them prove that before each merge?

## Trade-offs

- An outside suite is slow to build where none exists; recorded inputs and outputs are quicker but
  freeze the old bugs as expected behaviour (TST-3, TST-5).
- Locking tests against agent edits protects the oracle and slows legitimate test fixes, which
  then sit until a person approves them (OVS-1).
- A side-by-side run catches what tests miss, at the cost of making the old output deterministic
  first (TST-13).

## When not to apply it

- When the tests are what moves (a test-framework change), the suite cannot judge itself; compare
  counts and intent instead (TST-8).
- An owner who chose to fix known old bugs during the move gives up exact equality with the old
  system on those paths, by design (TST-3, PLN-5).
