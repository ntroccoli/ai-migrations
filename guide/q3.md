# Q3 guide: Can an agent build, check and test alone, fast, and in parallel, in both toolchains?

For question 3 of the [checklist](../checklist.md): read it before writing up a finding on that
question. It walks through what the cases show; the project's owner decides. Each point names its
evidence: a lesson ID (its strength, its cases and the cases against it are in
[lessons/evidence.md](../lessons/evidence.md); its page links the case sections) or a case link.
"(ours)" marks the maintainer's reading, evidence level `ours`; so does a lesson tagged `[ours]` there,
which is our inference from its cases.

## Lessons behind it

- [OPS-1](../lessons/operations.md): parallel agents saturated CPU, disk and I/O; one build at a
  time, through a lease, kept the machine usable.
- [OPS-2](../lessons/operations.md): operating-system limits contained heavy tests; asking the
  agent to be careful did not.
- [OPS-3](../lessons/operations.md): agents spend their time reading, building and testing, so a
  fast inner loop comes before more agents.
- [ORC-1](../lessons/orchestration.md): agents sharing one working copy wrecked each other's work.
- [ORC-2](../lessons/orchestration.md): parallel agents only on changes that are independent by
  design.
- [VER-2](../lessons/verification.md): cheap checks first, and a candidate dropped at its first
  failure.
- [VER-4](../lessons/verification.md): one verify tool that returns short errors.
- [TOL-6](../lessons/tooling.md): formatters, linters and type checks inside the agent's loop.
- [TOL-8](../lessons/tooling.md): a way to drive the running app directly, not through
  screenshots.

Cases, in our words: GitHub needed a build lock. Bun's agents sharing one checkout undid each
other's work within minutes, and heavy tests stalled the machine. 1Password and Spartacus gave
each agent a worktree (Spartacus's tests failed to start there); Spotify's verify tool returns
short errors. Shopify's agents took minutes per test in simulators; Asana's lint was slow and CI
disagreed with local runs.

## What it looks like in a project

- One command builds, lints and tests a unit, and its failure output is short enough to read in
  one go ([Spotify](../cases/2025-11-06-spotify-honk.md#what-worked)).
- A test run that needs a running service, a simulator or a manual step the agent cannot do
  (TOL-8).
- Timings recorded in CI history, or none, so they must be measured from fresh clones (ours).
- Two agents building at once slow each other or fight over one checkout ([Bun](../cases/2026-07-08-bun-zig-to-rust.md#what-went-wrong)).

## Questions to ask of this project

- What is the one command for one unit, in the old stack and in the target?
- How long does it take, and how many lines does a failure print?
- What happens when two fresh clones build and test at once on this machine?
- How are agents kept from undoing each other's work, and which platforms can their machines build?
- For an app: how does an agent drive it, and how long does one test take?

## Trade-offs

- A worktree per agent keeps agents apart cheaply, but some test setups fail to start in one; a
  full clone costs disk and install time (ORC-1).
- A build lease keeps the machine usable at the price of agents waiting their turn (OPS-1).
- Making the inner loop faster first delays the port and pays back on every later run (OPS-3).

## When not to apply it

- A single agent working alone needs no parallel measurement; the timing of one unit still
  matters (ours).
- Worktrees are only ruled out for measuring the repository, since they write into its `.git`;
  for the port itself they kept agents apart (ORC-1).
