# Q11 guide: How will changes reach users?

For question 11 of the [checklist](../checklist.md): read it before writing up a finding on that
question. It walks through what the cases show; the project's owner decides. Each point names its
evidence: a lesson ID (its strength, its cases and the cases against it are in
[lessons/evidence.md](../lessons/evidence.md); its page links the case sections) or a case link.
"(ours)" marks the maintainer's reading, evidence level `ours`; so does a lesson tagged `[ours]` there,
which is our inference from its cases.

## Lessons behind it

- [ROL-2](../lessons/rollout.md): merged and released as separate gates; a canary or pre-release
  first.
- [ROL-3](../lessons/rollout.md): slow production rollouts watched by owners; the pipeline speeds
  the code, not this step.
- [ROL-5](../lessons/rollout.md): short-lived agent branches against a busy main branch.
- [ROL-7](../lessons/rollout.md): a new failure boundary shipped as an opt-in mode beside the old
  default.
- [ROL-10](../lessons/rollout.md): shadow comparison aimed at the largest and oddest inputs, with
  mismatches labelled.
- [ROL-11](../lessons/rollout.md): cut over in order of how costly a mistake is to undo,
  read-only paths first.
- [VER-1](../lessons/verification.md): a green build shows the parts fit, not that behaviour
  survived.
- [OPS-5](../lessons/operations.md), [OPS-8](../lessons/operations.md): hardening after merge;
  headroom of shared services under double load.

Cases, in our words: GitHub aimed to ship each port to a pre-release first, yet some regressions
reached stable; Bun's merged build stayed a canary while regressions were fixed; Google rolled its
largest migrations out slowly, owners watching. Temporal compared every query and cut over
read-only paths first; GitLab ramped to full traffic past a divergence its shadow run flagged but
did not label. A rollback path per unit is ours.

## What it looks like in a project

- Release channels (pre-release, flags, canary) and the share of users each reaches
  ([GitHub](../cases/2026-09-16-github-copilot-runtime-rust.md#what-went-wrong), ROL-2).
- A shadow run whose mismatches are counted but not labelled by kind ([GitLab](../cases/2026-07-08-gitlab-rate-limiting.md#what-went-wrong)).
- One unit's change that cannot be rolled back without rolling back the rest (ours).
- A single-user or internal tool, where a release is a merge and a rollback is a revert (ours).

## Questions to ask of this project

- Which channels exist before stable, and who uses them?
- How are problems reported and watched after a release?
- How is one unit's change rolled back?
- Which paths are read-only and could go first?
- Not released yet: what must exist before the first release?

## Trade-offs

- A canary catches regressions before most users meet them and slows each release (ROL-2).
- A shadow run on real traffic finds divergences tests miss, at the cost of running both paths and
  of the shared services' headroom (ROL-10, OPS-8).

## When not to apply it

- A project not released yet has no channels to measure; the finding is what must exist before the
  first release (ours).
- A tool only its author runs gains little from staged rollout; a quick revert is its rollback
  (ours).
