# Q4 guide: How big is the job, really?

For question 4 of the [checklist](../checklist.md): read it before writing up a finding on that
question. It walks through what the cases show; the project's owner decides. Each point names its
evidence: a lesson ID (its strength, its cases and the cases against it are in
[lessons/evidence.md](../lessons/evidence.md); its page links the case sections) or a case link.
"(ours)" marks the maintainer's reading, evidence level `ours`; so does a lesson tagged `[ours]` there,
which is our inference from its cases.

## Lessons behind it

- [PLN-3](../lessons/planning.md): in a live repository, scope grew while the work ran, as code
  moved in and new code was written.
- [PLN-10](../lessons/planning.md): counting how often each pattern is used showed which
  transforms paid back first.
- [ROL-4](../lessons/rollout.md): deleting the old code in the change that adds the new turned
  concurrent edits into conflicts instead of silent losses.
- [TOL-1](../lessons/tooling.md): deterministic tools (analysers, call-site lists) built and
  reviewed first, then agents bound to them.
- [TOL-3](../lessons/tooling.md): change sites found with a code index or static analysis, erring
  on too many.
- [MSR-8](../lessons/measurement.md): finding the sites was often the hard part, done by tools,
  not the model.

Cases, in our words: GitHub's scope grew about threefold as code moved in and the old code kept
growing. Google's code index beat text search but listed irrelevant sites; 1Password's analyzer
listed every site.

## What it looks like in a project

- Code outside the folder being moved (shared helpers, generated files, templates, shaders) that
  must exist in the target too ([GitHub](../cases/2026-09-16-github-copilot-runtime-rust.md#what-went-wrong)).
- A change across call sites whose list came from text search, which misses uses reached through
  other variables ([Google](../cases/2025-04-13-google-int64-ids.md#what-went-wrong)).
- Code in scope still changing every week, so a port started now chases a moving target (PLN-3).
- Stored data (rows, hashes, saved files) the new build must keep reading (ours).

## Questions to ask of this project

- What must exist in the target that is not in the folder being moved?
- How were the call sites found, and is the list kept?
- How fast is the code in scope changing, and who is changing it?
- Which data formats and stored data must stay readable across the move?

## Trade-offs

- Waiting for the code to settle avoids chasing edits but delays the move; deleting old code in the
  porting change surfaces edits as conflicts, but takes away what a side-by-side run or a rollback
  may still need (ROL-4; row P3 of the checklist's Provenance table).
- A static analyzer lists every site and some irrelevant ones; text search is quicker and misses
  indirect uses (TOL-3).

## When not to apply it

- Where old and new must run side by side (question 2's differential run, question 11's
  rollback), deleting the old code in the porting change takes away what they run on (ROL-4).
- A fixed file set with no inflow, like a test-framework move, gains little from re-measuring
  scope while the work runs (PLN-3).
