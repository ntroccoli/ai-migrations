# Q6 guide: Is the end state written, and is the scope held?

For question 6 of the [checklist](../checklist.md): read it before writing up a finding on that
question. It walks through what the cases show; the project's owner decides. Each point names its
evidence: a lesson ID (its strength, its cases and the cases against it are in
[lessons/evidence.md](../lessons/evidence.md); its page links the case sections) or a case link.
"(ours)" marks the maintainer's reading, evidence level `ours`; so does a lesson tagged `[ours]` there,
which is our inference from its cases.

## Lessons behind it

- [CTX-4](../lessons/context.md): a stated end state, its preconditions and when not to act; vague
  goals were read narrowly.
- [PLN-2](../lessons/planning.md): most of the effort went into specs, guides and tooling before
  the bulk run.
- [PLN-5](../lessons/planning.md): translate first, redesign later, so a failure points at the
  port; several moves built the target's design first and disagree.
- [PLN-13](../lessons/planning.md): in a framework or data-store move, the target's foundation
  built first in its own idiom.
- [REV-4](../lessons/review.md): an automatic check comparing each diff with its instruction.
- [AGF-2](../lessons/agent-failures.md): agents fill gaps in the spec with plausible guesses.
- [AGF-4](../lessons/agent-failures.md): agents stray beyond the task.

Cases, in our words: GitHub's agents ported only the hot paths until the full end state was
written, and each redesign allowed mid-port cost regressions, time or tokens. Bun wrote a porting
guide first and left idiomatic code for later. 1Password's call-site cleanup ran from a list,
templates and escalation rules; Spotify's judge rejects sessions mostly for straying from the
prompt. Two other moves built the target's design first.

## What it looks like in a project

- A written target for the whole migration, with before-and-after examples from this repository
  ([GitHub](../cases/2026-09-16-github-copilot-runtime-rust.md#what-went-wrong), [Bun](../cases/2026-07-08-bun-zig-to-rust.md#what-worked)).
- Sites grouped into patterns, each with a template, and named conditions under which the agent
  asks a person (CTX-4, AGF-2).
- A repository rule that pushes deletion over translation ("delete old paths, keep no
  compatibility"), which works against translating first (PLN-5).
- An owner's recorded decision to redesign during the move (PLN-13).

## Questions to ask of this project

- Where is the end state written, for the whole migration and not one unit?
- Which patterns do the sites fall into, and is there a template for each?
- Under which named conditions should the agent ask a person?
- Does the plan translate first, or redesign as it goes, and who chose that?
- What checks each diff for changes outside its task?

## Trade-offs

- Translating first makes each failure point at the port; redesigning during it can save a second
  pass but mixes two causes of change (PLN-5).
- A narrow escalation rule keeps agents moving; a wide one ("ask whenever unsure") holds every unit
  until a person answers (CTX-4, row P4 of the checklist's Provenance table).
- Writing the end state and templates first is slow and is where the effort went in the cases
  that report it (PLN-2).

## When not to apply it

- A redesign the owner chose is their decision; the finding is its cost (two causes of change in
  one diff) and how to keep each change checkable, not a call to undo it (PLN-5's "Against",
  PLN-13).
- A small, uniform move (one API across call sites) may need only a template and a scope check,
  not a full end-state document (ours).
