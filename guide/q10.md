# Q10 guide: What may the agent decide and reach alone, and who reviews?

For question 10 of the [checklist](../checklist.md): read it before writing up a finding on that
question. It walks through what the cases show; the project's owner decides. Each point names its
evidence: a lesson ID (its strength, its cases and the cases against it are in
[lessons/evidence.md](../lessons/evidence.md); its page links the case sections) or a case link.
"(ours)" marks the maintainer's reading, evidence level `ours`; so does a lesson tagged `[ours]` there,
which is our inference from its cases.

## Lessons behind it

- [OVS-1](../lessons/oversight.md): edits to tests, snapshots, baselines and waiver labels need an
  owner's approval separate from the agent.
- [OVS-2](../lessons/oversight.md): the final merge kept with a person who checks how the agent
  answered CI and review.
- [AGF-1](../lessons/agent-failures.md), [AGF-5](../lessons/agent-failures.md),
  [AGF-9](../lessons/agent-failures.md): agents stubbed functions, used escape hatches and avoided
  the hard part.
- [SEC-1](../lessons/security.md), [SEC-2](../lessons/security.md),
  [SEC-3](../lessons/security.md): a minimal sandbox; whatever the harness exposes may get used;
  destructive commands blocked in the tool layer.
- [REV-1](../lessons/review.md), [REV-2](../lessons/review.md): reviewers in fresh contexts other
  than the writer; people on architecture and flagged risk.
- [REV-9](../lessons/review.md), [REV-11](../lessons/review.md): review by the owning teams became
  the bottleneck; reviewers who know the target platform.
- [TEM-4](../lessons/team.md), [TEM-6](../lessons/team.md): review in two tiers; the people doing
  it get drained.
- [ROL-9](../lessons/rollout.md): unrequested changes mostly sat undecided.

Cases, in our words: a GitHub agent applied a waiver label to pass a failing check, and a session
merged a peer's worktree unasked; Spotify's agents switched off unreliable tests; Bun's agents
stubbed functions until reviewer agents, seeing only the diff, rejected that; 1Password's agents
repeated ordering mistakes after being told. Most of Bloomberg's unrequested pull requests got no
decision from their owners; Shopify needed reviewers who knew the target platform.

## What it looks like in a project

- Guardrails an agent can switch off: a waiver label, a flag that skips a check, write access to
  snapshots ([GitHub](../cases/2026-09-16-github-copilot-runtime-rust.md#what-went-wrong), AGF-5).
- A rule written in agent instructions with nothing in CI or the tool layer enforcing it (SEC-3).
- Changes landing in other teams' code that did not ask for the move ([Bloomberg](../cases/2026-11-03-bloomberg-python-cpp-uplift.md#what-went-wrong)).
- One reviewer, who does not read the target language, with a few hours a week (REV-9, REV-11).
- A fresh reader who runs only after the merge: the faults it finds then cost a repair change
  each time, where before the merge they would have cost a revision (ours; seen in the
  maintainer's own project, not a published case; near REV-1).

## Questions to ask of this project

- Which guardrails could an agent switch off, and who must approve each?
- Which steps stay with people (schema changes, backfills, deploy order)?
- Which tools, skills and credentials can agent sessions reach?
- Which written rules does nothing enforce?
- Who reviews, do they read the target language, and how many hours a week do they have?
- Does a fresh reader read each large change before it is merged, or only after?

## Trade-offs

- Enforcing a rule in CI or the tool layer holds where an instruction did not, and costs setup and
  some false blocks (SEC-3).
- Reviewer agents in fresh contexts catch stubs and drift cheaply; their miss rate is unmeasured,
  so keeping the merge with a person is one option (REV-1, REV-5, OVS-2).
- Sending changes to other teams spreads the review load and leaves many changes undecided
  (ROL-9, TEM-4).

## When not to apply it

- A solo project where the owner is the only reviewer has no team to spread the load to; the
  hours a week still bound how fast agents' changes can land (ours).
- A sandboxed agent with no credentials needs fewer guardrails on what it can reach, not on what
  counts as correct (SEC-1, OVS-1).
