# Q5 guide: Can the work ship in small units, with old and new side by side?

For question 5 of the [checklist](../checklist.md): read it before writing up a finding on that
question. It walks through what the cases show; the project's owner decides. Each point names its
evidence: a lesson ID (its strength, its cases and the cases against it are in
[lessons/evidence.md](../lessons/evidence.md); its page links the case sections) or a case link.
"(ours)" marks the maintainer's reading, evidence level `ours`; so does a lesson tagged `[ours]` there,
which is our inference from its cases.

## Lessons behind it

- [PLN-1](../lessons/planning.md): the whole pipeline piloted on a few easy, well-tested units
  before the rest.
- [PLN-4](../lessons/planning.md): slices ordered along the dependency graph, leaves first, the hub
  last.
- [PLN-11](../lessons/planning.md): one-pass ports of a whole app gave code nobody could maintain,
  in one author's account; others disagree.
- [ROL-1](../lessons/rollout.md): one component swapped per change, old and new joined by a
  temporary bridge, so the main branch could always ship.
- [ROL-6](../lessons/rollout.md): the size of the bridge as the progress signal.
- [ORC-4](../lessons/orchestration.md): the work queue built from deterministic output, then fanned
  out.

Cases, in our words: GitHub swapped one component per pull request through a temporary interop
layer, leaves first; Intel went in dependency order; Google, Airbnb and Spotify moved one ID, file
or repository at a time. Bun made one switch after a small trial, and cycles left by its package
split took two more agent runs. Shopify's author says one-pass ports give code that cannot ship;
small reviewed checkpoints replaced them. The cost of a mixed build is ours.

## What it looks like in a project

- A seam where one unit can switch while the rest stays: a component boundary, an ABI, a process,
  a route ([pitfalls.md](../pitfalls.md#seams), ROL-1).
- Cycles between modules or files that keep any one of them from moving alone ([Bun](../cases/2026-07-08-bun-zig-to-rust.md#what-went-wrong)).
- Leaves that touch neither I/O nor shared state, the cheap first units (PLN-4).
- No seam at all, so the move is one switch (ours).

## Questions to ask of this project

- What are the units, and in what dependency order do they fall?
- How many cycles, and where?
- Which seam lets one unit switch, and how does the build link both languages meanwhile?
- What do the platform rules allow (a store's review, a plugin host)?
- Which units make a pilot that runs the whole loop?

## Trade-offs

- A bridge between old and new keeps the main branch shippable and costs a mixed build to
  maintain until it reaches zero (ROL-1, ROL-6).
- One switch after a small trial is faster and saves the bridge, but every regression lands at
  once (Bun, in [PLN-11](../lessons/planning.md)'s "Against").
- A pilot of a few units finds the loop's problems cheaply; it may miss problems that only appear
  at scale, such as agents clashing in one checkout (PLN-1).

## When not to apply it

- When the codebase has no seam and the owner accepts one switch, ordering units still helps the
  agents, though there are no small units to ship (ours).
- A pilot of a few easy files says little about code of several kinds; question 8 groups them
  (PLN-1, row P8 of the checklist's Provenance table).
