# Q1 guide: Is the move allowed, possible and worth it?

For question 1 of the [checklist](../checklist.md): read it before writing up a finding on that
question. It walks through what the cases show; the project's owner decides. Each point names its
evidence: a lesson ID (its strength, its cases and the cases against it are in
[lessons/evidence.md](../lessons/evidence.md); its page links the case sections) or a case link.
"(ours)" marks the maintainer's reading, evidence level `ours`; so does a lesson tagged `[ours]` there,
which is our inference from its cases.

## Lessons behind it

- [PLN-7](../lessons/planning.md): agents lower the price of a rewrite once shelved for cost, but
  the fair comparison is with doing nothing, not with a manual rewrite nobody would have funded.
- [PLN-8](../lessons/planning.md): parts that cannot be specified or checked (an unsupported
  platform, a language the model handles poorly) were left out rather than forced.
- [PLN-9](../lessons/planning.md): the published cases are success stories, so the odds they
  suggest run high; a partial outcome and a way to stop belong in the plan.
- [SEC-7](../lessons/security.md): each library the move replaces is a small migration of its
  own, above all security-sensitive ones.

Cases, in our words: the cases start from a known problem or forced move (GitHub's startup and
memory, Bun's crashes, Slack's blocked React upgrade, Google's int32 limit). The rest is ours.

## What it looks like in a project

- A written reason ties the move to a measured problem: a profile, a bill, a crash count, a
  limit about to be reached ([GitHub](../cases/2026-09-16-github-copilot-runtime-rust.md#what-was-migrated), [Google](../cases/2025-04-13-google-int64-ids.md#what-was-migrated)).
- The product rests on a framework (a renderer, a desktop shell, a store SDK) with no mature
  equivalent in the target, so the move is a rewrite on a new base rather than a port (ours).
- The repository's own rules pin the stack, forbid new libraries or name an approver; such a rule
  shapes the move before any measurement does (ours).

## Questions to ask of this project

- What problem does the move solve, and where is it measured?
- Is the code to port on the path where the time, memory or money goes?
- Which rule of the project's own speaks to the move: one that forbids the target, or one that
  only asks for an approver?
- Who maintains the result, and do they read the target language?
- What must the target win, in numbers, for the move to have been worth it?

## Trade-offs

- Moving for a measured problem gives a test of success; moving for fashion gives none, but a
  forced move (an end-of-life framework) may have no number and still be needed (PLN-7).
- A rewrite on a new base can fix design debt the port would carry over, at the price of losing
  the old code as the reference (PLN-5, PLN-13).
- Porting without the code's owners close to it saves their time now; in one case it made debugging
  and incident handling harder later, and other cases disagree (TEM-5).

## When not to apply it

- A rule that only names an approver is a question for that person, not a reason to hold the move
  (ours).
- When the owner has already decided to move for reasons outside the code (hiring, a vendor's end
  of support), the "worth it" part informs the plan rather than the decision (ours).
